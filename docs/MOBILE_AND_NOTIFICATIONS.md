# تطبيق النقاء والإشعارات — 17 أكتوبر 2026

## ما تم بناؤه
تطبيق واحد بموارد واجهة محلية باستخدام React وCapacitor، وليس تحويل الموقع إلى WebView يشغّل صفحة بعيدة. الزبون يحجز ويتابع كضيف؛ الإدارة والسائق يستخدمان Supabase Auth. الطلبات وتغييرات حالتها تتصل بواجهات HTTPS الموجودة ضمن المشروع.

- حجز بالاسم والهاتف والعنوان والخدمة والموعد، والتتبع برقم الطلب والهاتف.
- شاشة فريق تعرض الطلبات بحسب الدور. السائق يرى طلباته فقط، وتحديث حالته يمر عبر JWT وRLS وقيود انتقالات الحالة.
- Android وiOS native projects موجودان في `mobile/`، وواجهة التطبيق تُبنى وتنسخ إليهما عبر `npm run sync`.
- لا يوجد APK/IPA موقّع أو نشر على المتاجر. الماك الحالي يملك Command Line Tools فقط؛ فحص `java -version` لم يجد Java runtime و`xcodebuild -version` لم يجد Xcode الكامل. يلزم JDK المناسب لـ Android/Gradle وAndroid SDK وXcode للايفون وحسابات التوقيع.

## عند وصول طلب جديد
داخل معاملة حفظ أول سجل حالة، تُنشأ رسالة صندوق الإدارة وأحداث الإرسال في outbox؛ فشل الطابور يرجع العملية كاملة بدل إنشاء طلب بلا حدث. لا تُنسخ عناوين العملاء إلى الطابور.

1. لوحة الإدارة المفتوحة تفحص صندوقها كل 10 ثوانٍ، وتحدّث الطلبات وتصدر صوتًا إن فعّله المستخدم.
2. `after()` على إنشاء الطلب يوقظ المرسل بعد رد API، حتى لا يعتمد التنبيه على بقاء لوحة الإدارة مفتوحة.
3. إشعار الهاتف المغلق يذهب عبر FCM إلى أجهزة الإدارة المسجلة. يتضمن رقم الطلب فقط، ويحتاج Firebase وAPNs/Android إعدادًا فعليًا.
4. واتساب للعميل يُضاف عند موافقته الاختيارية وبحالات التأكيد والجدولة وخروج السائق للاستلام والاستلام والجاهزية وخروج السائق للتسليم والإكمال والإلغاء. الطلبات القديمة لا تعتبر موافقة.
5. يمكن إرسال واتساب إداري منفصل إذا ضُبط رقم المستلم وقالب الإدارة صراحةً.

`/admin/notifications` يعرض جاهزية الإعدادات وأعداد الحالات، بدون عرض المفاتيح. وجود المتغير ليس اختبارًا لصحة الاعتماد الخارجي.

## الإرسال وإعادة المحاولة
`claim_notifications` يحجز دفعة باستخدام SKIP LOCKED ومهلة حجز، ولا يمكن استدعاؤه من anon أو authenticated. الإرسال مقيد بالسيرفر. تسجل إيصالات نجاح كل جهاز حتى لا يعاد إرسال إشعار ناجح له عند فشل جهاز آخر.

الأخطاء المؤقتة يعاد جدولتها بحد أقصى خمس محاولات. غياب الإعداد لا يستنفد المحاولات. النتيجة غير المؤكدة (انقطاع الرد بعد الإرسال أو فشل حفظ الإيصال) تُوقف للمراجعة بدل الإعادة العمياء. لا يمكن ضمان exactly-once بين قاعدة البيانات وخدمة خارجية؛ يُستخدم eventId ثابت لتجميع إشعارات الهاتف، ولا يُدّعى استحالة التكرار.

يلزم مشغّل دوري لإعادة المحاولات حتى لو لم تكن لوحة الإدارة مفتوحة: شغّل `scripts/notification-worker.mjs` في عملية مستمرة أو استدعِ POST `/api/notifications/dispatch` كل دقيقة من scheduler مع `Authorization: Bearer <NOTIFICATION_WORKER_SECRET>`. لا تنشر سر المشغل في تطبيق الموبايل، ولا تضعه في URL. لم يتم تفعيل scheduler خارجي ضمن هذه المهمة.

## Firebase
1. أنشئ مشروع Firebase أو اختر مشروع المغسلة الصحيح، ثم سجل تطبيق Android وiOS بالمعرف التطويري `com.alnaqaa.laundry` (يُراجع قبل المتاجر).
2. ضع `google-services.json` في `mobile/android/app/` و`GoogleService-Info.plist` ضمن Target التطبيق في Xcode. الملفات مستثناة من Git.
3. فعّل Push Notifications capability في Xcode واربط مفتاح APNs بحساب Firebase. Background remote notifications وأحداث AppDelegate مجهزة بالكود؛ التوقيع والـ provisioning غير مجهزين.
4. ضع بيانات حساب خدمة ذي صلاحية FCM محدودة في `FIREBASE_SERVICE_ACCOUNT_JSON` على السيرفر فقط.
5. سجّل الدخول كإدارة من جهاز فعلي واضغط «فعّل إشعارات الطلب الجديد». لا يطلب التطبيق إذن الهاتف تلقائيًا من الزبائن.
6. جرّب طلبًا مصرحًا به والتطبيق مفتوح، بالخلفية، والهاتف مقفل. اختبر سحب الإذن وتسجيل الخروج وتبديل الحساب وتجدد الرمز.

المراجع الرسمية: [Firebase HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api)، [Capacitor](https://capacitorjs.com/docs)، [إضافة Firebase Messaging](https://capawesome.io/docs/sdks/capacitor/firebase/cloud-messaging/).

## WhatsApp Business Platform
واتساب على الهاتف وحده لا يهيئ Cloud API. يجب إكمال تسجيل Meta/WhatsApp Business Platform والتحقق من الرقم وقوالب Utility. لا تحذف أو تفصل حساب الهاتف الحالي؛ تحقق من مسار coexistence المتاح أو استخدم رقم اختبار قبل أي نقل للرقم.

متغيرات السيرفر موثقة في `.env.example`: token، phone number ID، إصدار Graph المعتمد بحساب Meta، اسم القالب ولغته، App Secret وVerify Token. لا يُفترض إصدار API أو قالب موجود بلا إعداد فعلي.

- قالب العميل المقترح `naqaa_order_update`، Body: `طلبك {{1}} لدى مغسلة النقاء: {{2}}. لمتابعة الطلب افتح موقع المغسلة. لإيقاف رسائل التحديث أرسل STOP.` — متغيران بالترتيب: رقم الطلب، وصف الحالة.
- قالب الإدارة المقترح `naqaa_new_order`، Body: `وصل طلب جديد {{1}} إلى مغسلة النقاء. افتح لوحة الإدارة لمراجعته.` — متغير واحد.
- هذه القوالب مسودات محلية؛ لم تُرسل للموافقة من Meta.
- سجّل callback `/api/whatsapp/webhook`، تحقق GET ثم subscribe to messages. POST يتحقق من HMAC قبل أي تعديل، ويسجل sent/delivered/read/failed دون الرجوع من read إلى حالة أقدم.
- رسائل STOP / unsubscribe / إلغاء / الغاء / توقف / وقف تسحب موافقة الهاتف من الطلبات الموجودة. لا يتم حفظ نص الرسالة الواردة.

مرجع Meta: [مجموعة WhatsApp الرسمية](https://www.postman.com/meta/whatsapp-business-platform/overview).

## الإعداد والتشغيل المحلي
من جذر المشروع `npm ci` وفحوص الموقع. داخل `mobile`: `npm ci`، ثم إعداد `.env.local` من `.env.example` ببيانات Supabase العامة فقط، ثم `npm run build` و`npm run sync`، وفتح Android Studio أو Xcode عبر السكربتات.

لا تستخدم service-role أو Meta token أو Firebase private key في أي متغير يبدأ بـ VITE_ أو NEXT_PUBLIC_. عنوان API يجب أن يكون HTTPS في نسخة الإنتاج، ولا يُستخدم server.url/allowNavigation إلى مواقع بعيدة داخل Capacitor.

## حالة التحقق
- اختبارات محلية لسياسات الإشعارات، موافقة العميل، حجز الدفعات بدون تكرار، قوالب واتساب، توقيع webhook ورفض العبث، إلغاء الاشتراك، وعدم رجوع delivery status.
- نجاح بناء واجهة الموبايل ومزامنة مشاريع المنصتين، وبناء الموقع وTypeScript.
- فحص الشاشات بالمتصفح المحلي؛ لا يوجد اختبار إرسال فعلي أو اختبار جهاز حقيقي أو بناء APK/IPA أو نشر على المتاجر.
- لوحة Firebase واجهت خطأ تحميل حالة شروط الاستخدام، وMeta طلب تسجيل الدخول. لم تُنشأ مفاتيح أو مشاريع خارجية أو تُقبل اتفاقيات ضمن المهمة.

تحديث خروج السائق: `on_the_way` يرسل «السائق في الطريق لاستلام أغراضك. يرجى تجهيزها للاستلام.» و`delivering` يرسل «السائق في الطريق لتسليم أغراضك بعد الغسيل. يرجى الاستعداد للاستلام.». تحديث السائق من الويب يمر بنفس مسار الهاتف لتشغيل الإرسال بعد حفظ الحالة. طبّق 0005 بعد 0004 عند التفعيل؛ لا إعادة إرسال بأثر رجعي.

## إدارة المغسلة من تطبيق الهاتف — 2026-10-18
- إدارة الطلب: تفاصيل العميل والخدمة والموعد والملاحظات، اختيار السائق وترتيب الزيارة وعدد القطع والحالة، المبلغ النهائي والتحصيل النقدي. حفظ التعديل يرفض النسخة القديمة عند اختلاف الحالة أو updated_at.
- طلبات المحل بمفتاح إعادة محاولة، سجل الحالات، بحث ضمن الطلبات المحمّلة، فلترة بالسائق والحالة والتاريخ وتحميل طلبات أقدم، ومجاميع مالية مسماة بوضوح للمعروض فقط.
- السائقون: إضافة بيانات وتعديلها وتفعيل/تعطيل. لا ينشئ هذا حساب Supabase Auth أو يربط profile تلقائيًا. لا حذف نهائي للطلبات ضمن شاشة الهاتف؛ الإلغاء متاح من الحالة.
- يستخدم عميل Supabase العام مع جلسة الإدارة وRLS الموجودة؛ لا يوجد مفتاح خدمة داخل التطبيق ولا migration جديدة. إرسال الإشعارات يستيقظ عبر المسار الإداري الحالي بعد الحفظ.
- لا تغيير ألوان أو خلفية. اختبارات تحقق البيانات وصلاحيات الإدارة/السائق وطلبات المحل والحفظ المتعارض محلية؛ لا تعتبر دليلًا على اكتمال تجربة كل إجراء بالقاعدة الحية.
