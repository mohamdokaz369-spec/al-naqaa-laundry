# Supabase — تطبيق التغييرات الأمنية

هذا الدليل لم يُنفَّذ بعد على قاعدة الإنتاج — كل شيء هنا مُجهَّز محليًا فقط
كما طُلب. اتبع الخطوات بالترتيب على بيئة تجريبية (staging) أولًا إن أمكن.

## 0) ما يجب التحقق منه أولًا على مشروع Supabase الحالي (قبل أي تعديل)

لم يكن بالإمكان الاتصال بمشروع Supabase الحي من هذه البيئة (لا توجد
بيانات اعتماد/`.env` محليًا). قبل تطبيق أي شيء أدناه، تحقق يدويًا:

1. **شغّل `supabase/check_existing_policies.sql` كاملًا** (SQL Editor في
   لوحة Supabase، أو `psql`) **قبل** تطبيق الـ migration. السؤال الذي
   يجيب عنه: هل توجد سياسة RLS قديمة بأي اسم آخر (مثلًا سياسة تسامحية
   أنشأها Table Editor تلقائيًا مثل "Enable read access for all users")
   على `orders`/`drivers`/`order_status_history`/`profiles`؟
   migration رقم `0001` يحذف فقط السياسات التي يعرف أسماءها (التي ينشئها
   هو نفسه) عبر `drop policy if exists "<name>"` — ولا يلمس أي سياسة
   أخرى بأي اسم مختلف. إن وُجدت سياسة تسامحية (permissive) قديمة تسمح
   لـ anon بالقراءة/الكتابة، فستبقى فعّالة **بجانب** السياسات الجديدة
   (Postgres يجمع السياسات التسامحية بـ OR)، ولن يكون هناك أي حجب فعلي
   لـ anon رغم تطبيق الـ migration. **لا تفترض أن anon محجوب حتى يعطيك
   هذا الفحص قائمة فارغة من "UNKNOWN POLICY".**
2. **Table Editor → orders**: تأكد من الحقول الفعلية (أسماء الأعمدة)
   تطابق `lib/types.ts` قبل تطبيق الـ migration — الـ triggers الجديدة في
   القسم 6/7 من الـ migration تذكر كل أعمدة `orders` بالاسم.
3. **Project Settings → API**: انسخ `service_role key` بحذر شديد — هذا
   مفتاح يتجاوز RLS بالكامل، يُستخدم فقط في متغير بيئة خادم
   `SUPABASE_SERVICE_ROLE_KEY` (بدون `NEXT_PUBLIC_`) ولا يُشارك أبدًا.

## 1) تطبيق الـ migration

```bash
npx supabase login
npx supabase link --project-ref <project-ref>   # من رابط مشروعك في لوحة Supabase
npx supabase db push                             # يطبّق supabase/migrations/0001_auth_roles_and_rls.sql
```

أو ببساطة: افتح **SQL Editor** في لوحة Supabase، الصق محتوى
`supabase/migrations/0001_auth_roles_and_rls.sql`، وشغّله.

هذا الملف **لا يحذف أو يعدّل أي صف موجود** — فقط يُنشئ جدول `profiles`،
يُفعّل RLS وسياساته، ويضيف trigger-ين يقيّدان أعمدة/انتقالات الحالة التي
يستطيع السائق تعديلها (تفصيل في القسم 7 أدناه).

⚠️ بعد تفعيل RLS مباشرة، ستتوقف كل الصفحات الحالية (`/admin/*`, `/driver`)
عن العمل حتى تُطبَّق تعديلات الكود المرفقة في نفس هذا التغيير (تسجيل دخول
Supabase Auth الحقيقي) — الاثنان يُطبَّقان معًا، وليس أحدهما بدون الآخر.

**مباشرة بعد التطبيق، أعد تشغيل `supabase/check_existing_policies.sql`**
(الاستعلام الثاني فيه، "UNKNOWN POLICY") — يجب أن يرجع **صفر صفوف**. أي
صف يظهر هو سياسة قديمة لم يصنعها هذا الملف، راجعها بنفسك قبل أي قرار
(الاستعلام الرابع في الملف يولّد نص `DROP POLICY` لمراجعتك، لا تُنفَّذ
تلقائيًا أبدًا).

## 2) إنشاء أول حساب أدمن

في **Authentication → Users** بلوحة Supabase، أنشئ مستخدمًا جديدًا
(بريد إلكتروني + كلمة مرور قوية) — أو عبر SQL Editor:

```sql
-- بعد إنشاء المستخدم من لوحة Authentication، اربطه بدور admin:
insert into public.profiles (id, role)
values ('<auth-user-uuid-من-لوحة-Authentication>', 'admin');
```

سجّل الدخول بهذا الحساب من `/admin/login`.

## 3) إنشاء حسابات السائقين

اخترنا **بريد إلكتروني + كلمة مرور** (عبر Supabase Auth) لتسجيل دخول
السائقين بدل "رقم الهاتف فقط" القديم، لأن تفعيل OTP برسائل SMS يتطلب ربط
مزوّد SMS (Twilio وغيره) من لوحة Supabase أولًا — وهذا إعداد يتم من
اللوحة مباشرة ولا يمكن إنجازه من الكود وحده. يمكن التحوّل إليه لاحقًا دون
تغيير بنية RLS.

لكل سائق:

```sql
-- 1) أنشئ مستخدم Auth له (من لوحة Authentication → Users → Add user)
-- 2) اربطه بصف السائق الموجود في جدول drivers:
insert into public.profiles (id, role, driver_id)
values ('<auth-user-uuid>', 'driver', <drivers.id>);
```

السائق يسجّل الدخول من `/driver/login` بنفس البريد وكلمة المرور.

## 4) متغيرات البيئة المطلوبة (انظر `.env.example`)

| المتغير | أين يُستخدم | ملاحظة |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | متصفح + خادم | عام، آمن للكشف |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | متصفح + خادم | عام، آمن للكشف — الحماية الفعلية الآن من RLS وليس من إخفاء هذا المفتاح |
| `SUPABASE_SERVICE_ROLE_KEY` | خادم فقط (`app/api/**`) | **سرّي — لا تضف له `NEXT_PUBLIC_` أبدًا ولا تدفعه لأي مكان عام** |

تمت إزالة `NEXT_PUBLIC_ADMIN_PASSWORD` نهائيًا من الكود — احذفه من إعدادات
Vercel بعد نشر هذا التغيير (لم يعد مستخدَمًا، ووجوده متروكًا يُبقي كلمة مرور
قديمة مكشوفة بلا داعٍ).

## 5) بعد التطبيق — تحقق يدوي (كل بند هنا لم يُختبر فعليًا من هذه البيئة — لا اتصال بقاعدة حقيقية)

- حاول فتح `/admin/orders` بدون تسجيل دخول → يجب أن تُحوَّل لـ `/admin/login`.
- حاول فتح `/driver` بدون تسجيل دخول → يجب أن تُحوَّل لـ `/driver/login`.
- سجّل دخول كسائق وتأكد أنه يرى طلباته المعيّنة فقط (جرّب استعلام مباشر
  بمفتاح الـ anon من خارج التطبيق لتتأكد أن RLS فعليًا يمنع رؤية طلبات
  سائق آخر، وليس فقط أن واجهة التطبيق تُخفيها).
- **عطّل سائقًا تجريبيًا** (`update drivers set is_active = false where id = ...`)
  وتأكد أن جلسته الحالية (إن كانت مفتوحة) تفقد الوصول فورًا: لا يرى طلباته،
  ولا يستطيع تعديل أي صف — بدون الحاجة لتسجيل خروج/دخول. هذا يتحقق من
  `current_driver_id()` في الـ migration.
- **حاول من جلسة سائق (ليس أدمن) تعديل حقل ممنوع مباشرة عبر طلب Supabase**
  (مثلًا `update drivers set name = 'x' where id = <own id>`، أو
  `update orders set customer_name = 'x' where id = <own order>`، أو
  `update orders set status = 'washing' where id = <own order and status='assigned'>`
  وهو انتقال غير مسموح) — يجب أن يفشل كل ذلك برسالة الخطأ من trigger، لا
  أن ينجح بصمت. هذا يتحقق من section 6/7 في الـ migration.
- **أرسل طلب استلام حقيقي من `/request-pickup` (أو استدعِ `/api/orders`
  مباشرة) بعد تطبيق الـ migration** وتأكد أن رقم الطلب (`order_number`)
  يُحفظ بنجاح ولا تظهر رسالة "حدث خطأ في تعيين رقم الطلب". هذا الخطوة
  بالتحديد تتحقق من أن trigger القسم 6 **لا يحظر** تحديث service-role
  لـ `order_number` بعد الإدراج — كان هذا خطأً أصلحناه (التحقق القديم كان
  يستثني `is_admin()` فقط، وservice-role ليس له `auth.uid()` فيُرفض خطأً).
- تأكد أن `/track-order` و`/track/[id]` ما زالا يعملان عبر `/api/track`
  الجديد، وأن طلب GET مباشر لجدول `orders` بمفتاح anon (دون تسجيل دخول)
  يُرفض الآن من Supabase نفسه (لا فقط من واجهة الموقع) — **وتأكد أولًا أن
  فحص `check_existing_policies.sql` رجع قائمة UNKNOWN POLICY فارغة**،
  وإلا فهذا الاختبار قد ينجح أو يفشل بالصدفة بحسب تلك السياسة القديمة.

## 6) معروف ومحدود عن قصد (وثّقه بوضوح، لا تتجاهله)

- الـ Rate limiting في `app/api/orders` و `app/api/track`
  (`lib/rate-limit.ts`) هو في الذاكرة فقط لكل نسخة خادم — تخفيف جيد ضد
  إساءة بسيطة، **وليس** حماية كافية ضد هجوم موزّع حقيقي. قبل أي حملة
  تسويقية كبيرة أو نمو حقيقي، انقله إلى تخزين مشترك (Upstash Redis +
  `@upstash/ratelimit`) أو فعّل Vercel Firewall أمام هذين المسارين.
- `/driver/login` بالبريد وكلمة المرور، وليس OTP برقم الهاتف — قرار عملي
  بسبب الحاجة لإعداد مزوّد SMS من لوحة Supabase أولًا (انظر القسم 3).
- تعطيل سائق (`is_active = false`) يقطع وصوله لقاعدة البيانات فورًا (عبر
  `current_driver_id()`)، لكنه لا يُلغي جلسة Supabase Auth الخاصة به
  (الـ JWT يبقى صالحًا لمدته الطبيعية إن كان محفوظًا عند المستخدم —
  لكنه يصبح بلا أي صلاحية RLS فعليًا). لإنهاء الجلسة فورًا أيضًا، استخدم
  `supabase.auth.admin.signOut(user_id)` من لوحة Supabase أو Admin API.
- هذا الملف وملف `check_existing_policies.sql` لم يُشغَّلا فعليًا على أي
  قاعدة Supabase حقيقية من هذه البيئة — راجع `WORK_STATUS.md` لقائمة ما
  اختُبر فعليًا (tsc/build/lint) وما لم يُختبر (كل ما يتعلق بـ Supabase
  حي).

## تحديث 16 أكتوبر 2026 — ترتيب التطبيق

- `0000_base_schema.sql`: تأسيس الجداول لقاعدة فارغة. لا يضيف الأعمدة الناقصة لجدول موجود. قارن schema الفعلية أولًا.
- `0001_auth_roles_and_rls.sql`: الأدوار وقيود السائق. استثناء السيرفر يستخدم دور `service_role` صراحةً.
- `0002_order_integrity.sql`: رقم طلب داخل INSERT، سجل تلقائي للحالات داخل نفس المعاملة، مفتاح منع التكرار، وجدول للحد المشترك للمحاولات.
- لا تعِد تشغيل `0001` بعد `0002`: يعيد سياسات إدخال سجل الحالات القديمة. فحص السياسات المحدث يتوقع سياسات `0002`.
- قبل النشر طبق واختبر على staging. الواجهة الجديدة تعتمد على `0002`؛ تعطل التخزين المشترك للمحاولات يجعل API يعيد 503 بدل السماح بطلبات غير محمية.
- رقم واتساب من `NEXT_PUBLIC_BUSINESS_WHATSAPP_NUMBER`. عند غيابه يظهر بديل للتواصل داخل الموقع.
- المواعيد الحالية يوميًا 09:00–18:00 بتوقيت Asia/Jerusalem، حسب تأكيد صاحب المغسلة.

### اختبار قبول مطلوب على القاعدة التجريبية
1. إنشاء طلب يعيد رقمًا ويولّد سجل حالة واحدًا.
2. إرسال طلبين متزامنين بنفس مفتاح UUID ينتج صفًا واحدًا ورقمًا واحدًا.
3. تغيير حالة ثم افتعال فشل في سجل الحالات يجب أن يرجع المعاملة كاملة دون تغيير الحالة.
4. السائق لا يعدل غير حالته وموقعه، ولا يضيف سجلات تاريخ يدويًا، ولا يصل لطلبات سائق آخر.
5. تعطيل السائق يمنع الوصول من جلسة مفتوحة أيضًا.
6. رفض anon للقراءة والكتابة المباشرة، مع مراجعة السياسات القديمة.
7. حد المحاولات يعمل من أكثر من نسخة خادم، وانقطاع القاعدة يعطي 503.
8. اختبار الدخول والخروج وتجديد الجلسة على الهاتف، ودورة استلام وغسيل وتوصيل وطلب داخل المحل.

وجود هذه القائمة لا يعني أن الاختبارات نُفذت. لا يوجد اتصال SQL مثبت ضمن هذه المهمة.

## نتيجة التحقق المحلي في هذه المهمة
نجح تنفيذ migrations بالترتيب على PostgreSQL مؤقت (PGlite 0.5.10). نجحت اختبارات RLS وعزل السائق وتقييد أعمدته، إنشاء رقم الطلب، رفض التكرار، تسجيل الحالات التلقائي والرجوع عن تحديث الحالة عند فشل سجلها، منع تحصيل بلا مبلغ، وحفظ حد المحاولات. auth.uid/auth.role والأدوار حُوكيت محليًا؛ لا يعني ذلك التحقق من جلسات Auth أو grants والسياسات القديمة على Supabase الحقيقي.
